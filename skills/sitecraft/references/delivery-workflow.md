# 从首屏到交付

新建或整体重做先按 [阶段产物与执行约束](workflow-contract.md) 建立七阶段记录。本文说明设计决策与实现方法。每阶段的实际产物、检查、失败修复和最终交付状态由阶段工具核对。

## 先做视觉选择

从用户原话确定最重要的感受、一个访客动作和能代表品牌的主体。已有品牌规范和用户指定的参考优先。对其他新站，按 [参考索引](design-library.md) 找一个真实案例，打开页面或看清实际截图。主案例至少能解释主体和另外两项如何互相配合：光线或材质、排字、构图。行业相近但气质相反的案例只用于补操作。白底、字号大或有动效这类单一相似点不足以定方向。能说明具体缺口时再找第二例。浏览受限时用已有品牌资料或内置案例，记录实际看到了什么。

在工作说明或内部记录里写三行，直接进入实现：

- **主体和材质**写明主参考链接及实际观察，再写本项目会用什么画面、光线或材质。素材足以支撑用户最在意的感受时再采用。
- **排字和构图**用实际标题说明字重、断行和图文谁先被看到，写下手机会保留的主体部位。检查这个字重和画面放在一起时，是否仍表达同一种气质。
- **访客动作**写下入口文案、目标和摆放。若采用辅助案例，记录链接以及借用的单一做法。

首稿用实际入口、真实 DOM、手机布局、一个可操作入口和一段业务内容。主要入口的目标同时写入，例如选花按钮对应的花单区、预约按钮打开的演示弹层。主图和实际使用的字体同时落盘，再查看画面。主素材随手可用时直接用。需要生成时首稿前最多一次。素材不可用时用排字、现有图片或原创图形继续。工具安装、批量素材、附加构图和可选设计简报排到页面可打开后。需要用版式数据时，使用 [设计简报脚本](../scripts/prepare_design.py) 的候选作辅助，再写明实际采用的方向。[随包版式数据](landing-patterns.json) · [MIT 许可](landing-patterns-LICENSE.txt)

## 先过首屏硬检查

有现成 Node.js、Playwright 和浏览器时，由阶段工具调用 [浏览器脚本](../scripts/review_site.mjs)。本阶段 `start` 后指定实际主按钮，检查桌面 1440×900 和手机 390×844。

```sh
python3 /path/to/sitecraft/scripts/workflow.py check --run qa/sitecraft \
  --tool browser --primary '.hero a.primary' --primary-target '#flowers' \
  --playwright-module /project/node_modules/playwright
```

硬检查覆盖以下条件。

- 标题和主要入口完整落在两个初始视口，页面无横向溢出。
- 首屏可见图片已完成加载且能解码，已请求的字体没有加载失败或仍在加载。另行核对主视觉的 CSS 背景图和实际字形。
- 主要入口使用页内链接时，目标存在，主按钮可点击，点击后目标进入视口。按钮开启弹层时，追加 `--primary-target '#booking-dialog'`，检查点击后的目标可见性。其他链接和弹层的焦点、关闭行为另行操作复查。
- 页面无运行时错误、失败请求和 HTTP 错误。截图保留操作前的初始画面，操作结果写入 `review.json`。

阶段工具在首屏自动启用 `--draft` 并要求 `--primary`。空链接、缺目标、点击被拦截、目标无法到达都要修复，再复验，通过后才扩展整页。表单提交、跨页或外部交易入口需要在授权范围内另行验证，可用本地演示流程。脚本将这类入口报告为 `primary_action_unverified`，修复说明应区分未支持的检查与实际损坏的链接。

报告 `pass` 表示硬检查通过，`visual_review` 仍为 `pending`。报告 `fail` 时保留具体失败项，不能写成环境未验证。缺 Playwright 或浏览器会报告 `unverified`，可用已有预览工具完成相同检查并记录证据。使用隔离浏览器上下文。若检查要求改动工作区外的用户文件或浏览器资料，结束该次检查，切换已有预览。某个工具失败最多尝试一次可用的替代方式。确实无法验证时，交付说明保留未验证范围。

## 再评画面，决定是否扩展

查看两张实际首屏，将主案例和首稿放在一起，按下面顺序给出短结论。

1. **气质与识别**。引用用户最在意的要求，用画面说明主体、光线或材质、字重和构图哪里相互支持、哪里打架。把品牌名盖住，指出仍能让人认出这个主题的细节。
2. **构图与排字**。检查实际语言的断行、手机主体裁切、第一眼焦点和操作区域。已有可比旧稿时固定品牌、文案、主图和视口，再比较构图与排字。旧稿表达更成立时，保留旧方向或先修候选稿的根本问题。
3. **复看**。写一句“哪里有问题、改了哪里、改后在哪个视口确认”。先修最主要的视觉问题并复看，检查仍未通过时继续针对原因修复。阶段通过后收束细微背景色差和分隔线，再推进整站。

回归示例。用户说花店要“白底、简约大气、有浪漫感”。黑色重字与暖黄、高反差主图都很抢眼时，即使布局清楚、按钮在首屏，仍需要回到素材和标题的搭配。若主要参考只有白底留白，它只说明空间安排。重新选择能说明光线和字形关系的主案例，然后比较实际画面。

需要比较两种构图时，固定需求、品牌、文字、主图和视口。有意比较图像时另开一轮，只改变所评估的因素。A、B 用相同的截图等待时间。可选参考图使用相同视口，按原站的实际加载时间截取。

```sh
python3 /path/to/sitecraft/scripts/compare_reviews.py \
  qa/a/review.json qa/b/review.json --reference qa/reference/review.json \
  --brief '原始需求' --out qa/compare.html
```

对照页内嵌截图，可直接打开。用过的案例链接和视觉结论留在项目记录中。

## 完成网页，再做交付检查

看实际页面和主要交互，按 [视觉验收](visual-review.md) 检查内容节奏、手机重排、动效和键盘状态。整站阶段的浏览器检查自动包含减少动态效果环境与整页截图，并按契约指定主要操作目标。动态效果使用 `--motion-plan` 留下实际过程帧。3D 场景、海报与显式回退参数见 [3D 实现](web-3d.md)。脚本通过只代表已覆盖的检查。只有真正观察到动效和过渡才报告已验证。

需要静态部署包时，按 [静态发布检查](static-release.md) 优化并核对最终包，用现有工具测首页。用户要求离线单文件时以断网可打开为验收目标。交付时给可打开的网页、实际验证和仍有影响的待验证项。
